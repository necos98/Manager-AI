`issue_service.delete()` originally called `issue_store.delete_issue()` which only removes from RAM (`_core.delete`) and enqueues a background file delete. BackgroundWriter processes the queue with up to 500ms delay. During this window, any call to `load_issue()` for the deleted ID triggers disk fallback (files still exist) → `_core.upsert()` reinserts the issue into RAM, undoing the delete.

**Fix (2026-05-27):** `issue_service.delete()` now calls `issue_store.delete_issue_files()` synchronously after `issue_store.delete_issue()`. This immediately removes files from disk and rebuilds the index, closing the race window.

`delete_issue_files()` lives in `issue_store.py` and delegates to `delete_from_disk()` + `rebuild_index_for()` from `background_writer.py` (both renamed from private `_delete_from_disk` / `_rebuild_index_for` to public).

BackgroundWriter still processes the delete from the queue — idempotent since files are already gone. Same pattern should be applied to memory and file deletion if they exhibit the same race.

**Why:** RAM-first architecture means MemoryStore is the source of truth at runtime, but `load_issue()` has a disk fallback that rehydrates deleted records if files haven't been cleaned up yet. The async BackgroundWriter creates a window where deletes can be silently undone by any read.
