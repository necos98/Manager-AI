Analysis for "Force Finish" button feature:

Constraint model in backend:
1. `VALID_TRANSITIONS` in models/issue.py: NEW→REASONING, REASONING→PLANNED, PLANNED→ACCEPTED, ACCEPTED→FINISHED
2. `complete_issue()` enforces: status must be ACCEPTED, all tasks must be completed if tasks exist, recap required
3. `cancel_issue()` has NO constraints — any status → CANCELED directly. This is the pattern to mirror for force finish.
4. `update_status()` enforces VALID_TRANSITIONS, except CANCELED which is allowed from any state.

Frontend (issue-actions.tsx):
- IssueActions component shows conditional buttons based on status
- "Mark as Complete" only shows when status=Accepted
- "Cancel Issue" always shows (even from any status)
- `isTerminalState` (Finished/Canceled) hides all action buttons
- Confirm dialogs use Dialog component with ActionType union

Implementation approach (based on cancel_issue pattern):
- Backend: add `force_finish_issue()` method bypassing status+task constraints, sets status=FINISHED + finished_at + optional recap
- REST: add POST /{issue_id}/force-finish endpoint
- MCP: add `force_finish_issue` tool
- Frontend: add "Force Finish" button in IssueActions, available from any non-terminal status, with confirm dialog
