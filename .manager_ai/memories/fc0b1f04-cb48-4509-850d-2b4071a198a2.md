`PipelineService.add_step()` ignores the passed `order_index` parameter and always auto-assigns `MAX(order_index) + 1` (or 0 if no steps exist). This is append-only behavior — steps are always added to the end.

**Why:** The UNIQUE constraint on `(pipeline_id, order_index)` means duplicate order_index values fail. The frontend never sends `order_index` (it defaults to 0), so adding a second step always collided. Append-only is the simplest fix. For explicit reordering, use `reorder_steps()` which has a two-pass algorithm to avoid constraint violations.

**How to apply:** When adding pipeline steps programmatically (e.g., in `create_pipeline`), each `add_step()` call auto-increments even when called in a loop — each flush updates the max. The `order_index` parameter on the API schema still exists but is ignored by the service. If insert-at-position behavior is needed in the future, add it as a separate method and use the two-pass reorder pattern.
