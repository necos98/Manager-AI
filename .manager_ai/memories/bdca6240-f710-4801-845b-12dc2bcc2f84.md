6 pipeline tables organized into 3 model files:
- `agent.py` — Agent (standalone, reusable across pipelines/projects)
- `pipeline.py` — Pipeline + PipelineStep (pipeline definition)
- `pipeline_run.py` — PipelineRun + PipelineStepRun + PipelineMessage + PipelineRunStatus/PipelineStepRunStatus enums (execution records)

Key design decisions:
1. `agents.name` has UniqueConstraint(project_id, name) — agent names scoped per project, same name allowed in different projects
2. `pipeline_runs.issue_id` is a plain string (String(255)), NOT a ForeignKey — it may reference issues outside Manager AI
3. `pipeline_steps` has UniqueConstraint(pipeline_id, order_index) — no duplicate step ordering
4. `pipeline_step_runs.terminal_id` is Integer (nullable, SET NULL on delete) because `terminal_commands.id` is Integer while all other pipeline PKs are UUID strings
5. Cascade patterns: pipeline → steps (delete-orphan), pipeline_run → step_runs + messages (delete-orphan), project → agents + pipelines (cascade delete). Agent → PipelineStep has NO cascade (deleting agent should not delete step definitions). PipelineRun → Pipeline has NO cascade (keep run history when pipeline deleted). PipelineStepRun → PipelineStep has NO cascade.

**Why:** Grouping by lifecycle (definition vs execution). Enums co-located with models that use them. Cascade rules preserve history where important, clean up where ownership is clear.

**How to apply:** New pipeline-related models should follow the same file grouping. When adding FK relationships, check cascade rules against this baseline.
