In `frontend/src/shared/context/event-context.tsx`, the `buildToastContent` function uses a switch statement to decide which events produce toasts. Events that should be silent (no toast, no sound) but still trigger cache invalidation MUST be listed in the silent case block. If a new backend event type is added and not explicitly handled, it falls through to the `default` case and produces a toast with the raw event type string as title (e.g., "issue_updated").

**Silent events (as of 2026-05-04):** `project_updated`, `issue_updated`, `file_updated`, `memory_created`, `memory_updated`, `memory_deleted`, `memory_linked`, `memory_unlinked`, `task_updated`, `tts`.

**Watcher events:** `issue_updated`, `file_updated`, `memory_updated` — these come from the filesystem watcher rebuilding index files. They are cache-invalidation signals, not user-facing notifications.

**Why:** The watcher already debounces at 500ms per area, but each flush still emits one event per area. Without explicit silencing, each of these produces a toast with sound. User complained about "arrassment" of notifications from `issue_updated` events specifically.
