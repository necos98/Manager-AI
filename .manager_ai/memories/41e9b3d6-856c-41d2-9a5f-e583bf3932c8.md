`_issue_completion_locks` (`issue_service.py:38`) is a module-level dict that grows unbounded — every completed issue leaves a lock. Fix: pop the lock after the `async with lock:` block in `complete_issue()` completes.

**Why:** Module-level dicts persist for process lifetime, not request-scoped like instance attrs (see [[Service instance dicts work as natural request-scoped cache]]). Prior pattern: `_step_completion_events` in pipeline run service — same testability smell.

**How to apply:** After the `async with lock:` block in `complete_issue()` (line 394, after `return rec`), add `_issue_completion_locks.pop(issue_id, None)`. Only `complete_issue()` uses this lock — `cancel_issue()` and `force_finish_issue()` don't and shouldn't.

**Edge case:** Concurrent calls to `complete_issue()` on the same issue: first acquires lock and completes, second gets same lock ref (via `setdefault`), acquires after pop, fails with `InvalidTransitionError` — correct behavior.

**Test:** `test_complete_issue_blocks_when_lock_held` already tests lock behavior. After fix, its manual cleanup `_issue_completion_locks.pop(issue.id, None)` becomes a no-op — still correct.
