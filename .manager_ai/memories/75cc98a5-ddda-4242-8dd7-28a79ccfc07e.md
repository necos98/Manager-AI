Built-in plugin catalog system added May 2026. Key architectural decisions:

- **Catalog location**: `backend/plugins/<key>/plugin.yaml` — one folder per plugin, YAML manifest with name, description, transport, command/url, args, access_level, timeout, and `options` (list of OptionDef: key, label, type, required, default, placeholder, choices).
- **CatalogLoader singleton**: `backend/app/mcp/catalog.py`. Loads all manifests at startup via `catalog_loader.load()`. Called in main.py lifespan before `start_plugins_for_project`.
- **Translation layer**: `build_runtime_config(catalog_key, enabled, user_config)` merges catalog definition + per-project user config into existing `PluginConfig` — PluginManager internals unchanged. The translation layer is the key insight: instead of changing PluginManager, we transform data before it reaches PluginManager.
- **Plugin key = directory name**: No `catalog_key` indirection in plugins.yaml. The key in the plugins dict IS the catalog key.
- **Global catalog, per-project config**: Catalog loaded once. Project `plugins.yaml` v2 stores only `enabled` + `config` dict. User config values injected as env vars at runtime.
- **Catalog endpoint**: `GET /api/plugins/catalog` on separate router (no project_id prefix) since catalog is global.

Why: User wanted developers to add plugins to codebase, end users only configure options and enable. Chose manifest-driven (Approach 1) over Python module plugins — simpler, declarative, easy PRs.
