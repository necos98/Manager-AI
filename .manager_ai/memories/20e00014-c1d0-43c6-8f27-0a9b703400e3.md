Storage modules (`issue_store`, `memory_store`, `file_store`) use an in-process `ReadCache` (TTL dict, 30s) to skip repeated filesystem reads. No external dependencies.

**Key decisions:**
- Read-through only — writes stay synchronous. Async fire-and-forget would break index rebuild ordering (rebuild reads from disk right after write, needs latest data)
- Cache keys scoped by project_path: `{project_path}:{entity_id}` or `{project_path}:__index__`
- 30s TTL as safety net for external file modifications not caught by watcher
- Watcher invalidation is coarse (`cache.clear()`) — watcher only tracks area (issues/memories/files), not individual IDs
- `clear_all_caches()` called in test conftest autouse fixture for test isolation
- User explicitly chose in-process over Redis — cache must live inside Manager AI process, no external servers

**Why:** User reported sluggish navigation after flat-file migration. Every page navigation triggered fresh disk I/O (2N+1 file reads per issue list).
