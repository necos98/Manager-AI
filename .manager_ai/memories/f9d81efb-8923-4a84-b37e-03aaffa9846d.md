When calling `rebuild_issues_index()`, `rebuild_memories_index()`, or `rebuild_files_index()`, always follow with the corresponding `invalidate_*_cache()` call (prefix-based invalidation). The rebuild functions only invalidate the `__index__` cache key, not individual record caches. If individual issue/memory/file caches survive from a previous TTL window, they can serve stale data even though the index was rebuilt. The watcher `_flush()` already does this; `start_project()` and the new `rebuild-index` endpoint now also follow this pattern.

**Why:** Discovered during issue #48c90ba2 — `start_project()` only invalidated `__index__` after rebuild, which was fine at startup (empty cache) but wrong in principle and would break if start_project() is ever re-called on a running server.

**Rule:** rebuild + invalidate always go together. The rebuild updates the YAML on disk; the full prefix invalidation ensures no stale records lurk in the in-process cache.
