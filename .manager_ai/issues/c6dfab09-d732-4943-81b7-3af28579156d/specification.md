# Backend Error Logging System

## Problem Statement

Manager AI backend errors are inconsistently handled. The existing ErrorLoggerMiddleware catches HTTP request exceptions and writes JSON to daily aggregated files, but non-HTTP errors (background tasks, MCP plugin failures, database errors, terminal service failures, uncaught exceptions) have no file-based logging. Console output shows full stack traces at ERROR level, which the user considers noise. A unified per-error file logging system is needed.

## Scope

### What IS in scope

- A system that writes one plain-text log file per error occurrence to `backend/logs/`
- Capture of ALL significant backend errors, covering:
  1. **HTTP request errors** — exceptions raised during request handling (existing middleware territory)
  2. **Validation errors** — Pydantic/FastAPI validation failures
  3. **Database errors** — SQLAlchemy/aiosqlite connection failures, query errors, constraint violations
  4. **MCP plugin errors** — connection failures, tool call failures, plugin crashes
  5. **Terminal service errors** — PTY creation failures, WebSocket errors, WSL integration errors
  6. **Background task exceptions** — pipeline execution errors, async task failures, file processing errors
  7. **Uncaught exceptions** — `sys.excepthook` and asyncio exception handler level
  8. **Application-level errors** — exceptions raised via the existing `AppError` exception hierarchy
- Each log file must contain: timestamp, error type, message, source location, full stack trace, request context (when applicable), and relevant metadata

### What is NOT in scope (non-goals)

- Log aggregation, centralization, or shipping to external services
- Log rotation or auto-deletion — files persist indefinitely
- Console output changes — console format and level remain as-is (clean messages at ERROR, tracebacks at DEBUG only)
- Email or notification alerts on errors
- Real-time log streaming or WebSocket log delivery
- JSON or structured logging formats — only plain text (.log/.txt)
- Modifying the existing `logging.getLogger()` calls across 35+ modules individually
- Performance benchmarking or load testing of the logging system
- Dashboard or UI for viewing logs
- Encryption or access control on log files

## Requirements

### R1 — Per-error log files

Each distinct error occurrence MUST produce a single plain-text file in `backend/logs/`. Two errors raised within the same second MUST NOT collide — each gets a unique file.

### R2 — File naming

Log files MUST follow this naming convention:
```
error_YYYYMMDD_HHMMSS[_SUFFIX].log
```
Where:
- `YYYYMMDD` = date of the error
- `HHMMSS` = time of the error (24h)
- `_SUFFIX` = optional disambiguator appended when multiple errors share the same timestamp (random alphanumeric)

### R3 — Log file content

Each log file MUST contain the following sections, in order:

1. **Header divider** — visual separator with error type and timestamp
2. **Error classification** — error type (Python exception class or equivalent category), error message text
3. **Source location** — module path and line number where the error originated
4. **Request context** (only when tied to an HTTP request) — HTTP method, path, query parameters, client IP
5. **Full stack trace** — complete Python traceback, no truncation
6. **Metadata** — process ID, logger name, thread/process name

### R4 — Error source coverage

The system MUST capture errors from all of (Scope item 2). Each source must produce log files in the same unified format. Errors generated by the logging system itself (e.g. disk full, permission denied) must not cause cascade failures — file write failures are silently handled.

### R5 — Robustness

- Failure to write a log file MUST NOT crash or degrade the application
- Log writes are best-effort: if the directory is unwritable, the error is silently dropped (console logging still works)
- The system must handle concurrent error logging from multiple threads/async tasks without corruption

### R6 — Integration with existing infrastructure

- The existing ErrorLoggerMiddleware MUST continue to function during transition — the new system must be additive or carefully swapped
- The existing `logging.getLogger()` calls across the codebase must be captured automatically without modifying each call site
- The system must respect the existing logging philosophy: console output shows clean error messages, full tracebacks are reserved for log files and DEBUG level console

### R7 — Configuration

- The log directory path (`backend/logs/`) MUST be configurable via an environment variable `MANAGER_AI_LOG_DIR` with fallback to default
- No other runtime configuration is required

## Constraints

1. The `backend/logs/` directory must be created automatically if it does not exist
2. No external dependencies beyond Python standard library (stdlib `logging` module)
3. Must work correctly with both sync and async code paths
4. Must not introduce noticeable latency on error paths
5. File writes must use try/except guards to prevent cascade failures
6. Plain text only — no JSON, YAML, or structured formats in the log files

## Acceptance Criteria

- [ ] AC1: An uncaught exception anywhere in the backend produces a file `backend/logs/error_YYYYMMDD_HHMMSS[_SUFFIX].log` with timestamp, type, message, source, and full traceback
- [ ] AC2: An HTTP 500 error produces a log file with request context (method, path, query, client IP) in addition to the standard fields
- [ ] AC3: A validation error (HTTP 422) produces a log file
- [ ] AC4: A database connection failure produces a log file
- [ ] AC5: An MCP plugin disconnection or tool call failure produces a log file
- [ ] AC6: A terminal PTY creation failure produces a log file
- [ ] AC7: A background task exception (pipeline run failure) produces a log file
- [ ] AC8: Two errors at the same second produce two separate files (no overwrite)
- [ ] AC9: Writing to a read-only filesystem or full disk does not crash the backend
- [ ] AC10: The existing console logging behavior is unchanged (clean messages at ERROR, tracebacks at DEBUG only)
- [ ] AC11: After the new system is enabled, every HTTP request error type that the existing ErrorLoggerMiddleware was logging (JSON to daily files) is also captured by the new system — no regression in HTTP error coverage during or after transition
- [ ] AC12: Setting `MANAGER_AI_LOG_DIR=/custom/path` redirects log files to `/custom/path/`
